## Demo script (about 8 minutes)
1. Start backend and frontend; open the Landing page; point out the sample-data notice.
2. Discover: search "goa", filter by beach, open a destination, show attractions and best months.
3. Log in as the demo user (`demo@tourplan.ai` / `demo12345`).
4. New trip: start Mumbai, 3 travellers, 4 days, budget Rs 20,000, interests nature + food; submit.
5. Show the recommendation ranking and the **score breakdown** with reasons.
6. Open the itinerary; move an activity; save.
7. Budget tab: change a category, watch totals and over-budget warning; see cheaper alternatives.
8. Map tab: route line between stops; switch to list view.
9. AI assistant: type "Plan 3 days in Lonavala for 3 people under 15k"; show the source label (`rule_based` unless a key is set); then "make it cheaper".
10. Export the PDF; toggle the airplane transition off in Settings; log out.

## Viva questions
**Q1. Why FastAPI?**

Typed endpoints, Pydantic validation and automatic OpenAPI docs reduce boilerplate and errors.

**Q2. Why SQLite?**

Zero-setup relational store, enough for a demo; SQLAlchemy lets us move to PostgreSQL by changing the URL.

**Q3. How is the LLM used?**

Only to explain a plan the deterministic engine already built. Output is parsed as JSON and validated; failures fall back to rule-based text.

**Q4. What if there is no API key?**

The fallback explanation is generated by rules and labelled `rule_based`; it is never presented as an LLM.

**Q5. Where is the API key stored?**

Only in backend environment variables; the frontend never receives it.

**Q6. How does the recommendation score work?**

100 points: budget_fit 35, interest_match 30, season_fit 15, duration_fit 10, style_fit 10; each gives a reason string; in-budget first.

**Q7. Are prices real?**

No. They are indicative sample estimates and labelled so. The app does not book.

**Q8. How is the budget computed?**

Pure function; worked example total Rs 21,240 matches a unit test calculated by hand.

**Q9. How are passwords stored?**

bcrypt hashes; plaintext is never stored or logged.

**Q10. How do you stop users reading each other's trips?**

Every trip query filters by the current user; foreign ids return 404.

**Q11. What is JWT?**

A signed token containing the user id and expiry; the server verifies the signature on each request.

**Q12. What are the weaknesses of localStorage tokens?**

XSS can read them; httpOnly cookies with CSRF protection are safer (listed as future work).

**Q13. How is rate limiting done?**

In-memory sliding window per user for AI endpoints; resets on restart; Redis would be needed at scale.

**Q14. What does the ER diagram show?**

Users own trips; trips have days, activities, expenses and packing items; destinations have attractions.

**Q15. Why a deterministic engine plus LLM?**

Numbers and places must be reproducible and testable; LLMs may hallucinate.

**Q16. How is transport estimated?**

Haversine distance, road factor 1.25, indicative per-km rates, flight rule over 4000 km.

**Q17. How did you test?**

45 pytest functions cover budget math, travel, planner, AI extraction and API authorisation. Results must be run and pasted; none are claimed here.

**Q18. What does reduced motion do?**

Skips the plane transition automatically when the OS asks for reduced motion.

**Q19. What would you improve?**

Migrations, live pricing APIs, cookie sessions, larger dataset.

**Q20. What are the limits of the chat extractor?**

English keyword rules; it asks follow-ups when days or budget are missing.
